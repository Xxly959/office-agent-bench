# Office Agent Bench

衡量大模型 agent 完成中文办公任务的可靠性，重点回答：**模型说“完成了”的时候，结果可信吗？**

项目从会议待办抽取和表格筛选出发，逐步扩展到文件编辑、工具调用与多步流程。每次评测同时记录实际结果、完成声明和格式问题，保留原始输出及复核证据，让结论可以追溯。

**当前状态（2026-10-14）：第一阶段收尾。** 8 题的运行、确定性评分、日志导出、离线复现及 L2 变异测试已实现；作者人工复核与部分收尾事项仍待完成。第二阶段已有设计草案，文件检查器和沙箱尚未实现，未标记 `stage1-done`。

项目口径见 [PROJECT_SPEC](docs/PROJECT_SPEC.md)，执行入口见 [AGENTS.md](AGENTS.md)，评分细节见 [scorer_rules.md](docs/scorer_rules.md)。

## 研究问题与事前假设

| 问题 | 指标 | 事前假设 |
| --- | --- | --- |
| 单次能做对多少，多次运行稳不稳？ | pass@1、pass^k、每题通过次数 | 存在随机性时，连续多次全部正确的概率低于单次正确率。 |
| 声称完成却做错有多常见？ | 完成声明精确率、误报完成率、false_ok 率 | 不可完成或信息不全任务更容易出现不可信的完成声明。 |
| 失败发生在哪里？ | 从真实失败轨迹归纳分类 | 失败可能集中在编造、条件过滤、格式转换等少数类别。 |

这些是待检验的假设。预测写在运行之前，结果出来后单独对照，不回改预测。第一阶段的 [原预测](docs/predictions.md)完整保留；后来追加的模型名称说明明确标为运行后补记。

pass@1 对每题的通过比例取平均，题与题等权。pass^k 衡量随机选取 k 次运行全部正确的概率，不能简单把 pass@1 取 k 次方；重复输出没有可确认的随机性时，不据此宣称稳定性。

## 任务与评分设计

第一阶段冻结 8 条原创合成任务：easy 4、hard 2、adversarial 2。其中事项抽取 7 条、表格筛选 1 条；可完成 7 条、`cannot_complete` 1 条。按家族只报告计数，不报告小样本家族百分比。冻结提交和 SHA-256 见 [数据清单](docs/data_manifest.md)。

模型只返回一个 JSON 对象，顶层仅有 `status` 和 `items`。每个 item 仅有 `owner`、`task`、`deadline`：人名与事项名取自原文，负责人或截止日期缺失时按任务要求使用 JSON null，日期统一为 `YYYY-MM-DD`。v1 中没有符合条件的事项时，输出 `cannot_complete` 和空 items；文件任务中的不可完成语义须另行制定规则。

评分器按照 [v1 与 v1.1 规则](docs/scorer_rules.md)确定性判定，整题取 1 或 0：

- **结果与格式分开记录。** 合规 Markdown 围栏可剥离，但记录格式违规；内容全对、顺序不同可通过，但记录顺序违规。其他结构、类型和字段错误严格判定。
- **按 task 配对。** 指令要求复制事项名，因此它是配对依据；同名项一对一消耗，再检查负责人、日期、漏项和多项。
- **声明与正确性分开记录。** 已解析对象的原始 `status` 恰为 `ok` 时，`claimed_ok` 为真；误报完成为 `claimed_ok` 且结果错误。
- **冻结数据和规则。** 保留事前预测与历史结果，防止看到模型表现后调整口径。第二阶段先写家族协议与评分规则，再出题，并分开开发集与测试集。

确定性评分使相同输出得到相同结果；整题二值对应“交付是否完整正确”，漏项、多项等诊断另存，供失败分析。标准答案只进入宿主评分 metadata，不拼进模型消息；现有离线复核逐条检查了实际输入。

## 第一阶段结果

运行日期为 2026-10-13，模型为 `deepseek/deepseek-flash`，8 题各运行 3 次，共 24 次有效运行。

| 记录 | 结果与分母 |
| --- | --- |
| 正确 | 24/24 次；每题均为 3/3 |
| 声称完成（claimed_ok） | 21/24 次 |
| 误报完成 | 0/24 次有效运行 |
| 完成声明精确率 | 21/21 次完成声明正确 |
| false_ok | 0/3 次；来自同一道 cannot_complete 任务 |
| 格式违规 | 0/24 次 |
| 顺序违规 | 0/24 次 |
| API 最终失败 | 0 次 |

误报完成率的分母是全部有效运行；完成声明精确率的分母是完成声明次数。解析失败但可提取出 `status=ok` 的输出不计入主误报完成率，因此该口径一般是下界；本次没有这种输出。未来结果需分别报告内容错误与仅结构错误造成的误报完成，并单列 API 错误。

这些是 **8 题上的描述性计数**。当前未提供聚类置信区间或跨模型比较，不据此给出模型排名或泛化可靠性结论。

原始存档、逐次结果和事实汇总见 [results/](results/)，首次命令及配置证据见 [运行清单](results/run_manifest_stage1.md)。

## 局限与完成边界

- **样本量与覆盖有限。** 只有 8 题、两个家族，且只有一道 cannot_complete 任务。三次重复相关，不能把 24 次当作 24 道独立题。
- **标准答案由单一作者制作。** 作者独立复核尚未完成，当前不能宣称评分器与人工判断已达成一致。
- **任务仍偏结构化。** 抽取任务以明确事项名为配对依据；没有金标 deadline=null 的题，尚未评测 xlsx/docx 编辑、工具使用或多步代理流程。
- **评分采用严格主口径。** 围栏和顺序之外不放宽。S1–S3 敏感性分析、置信区间和多模型统计尚未实现，误报完成的下界限制需持续披露。
- **重复输出原因未明。** 每题三次最终文本一致，但 temperature、缓存等设置没有明确记录，不能把它解释为稳定性证据。
- **历史配置存在复现限制。** 首次日志为 dirty=True，部分生成参数未显式固定；存档可离线复核，再调用 API 不保证产生相同文本。完整传递依赖也尚未锁定。

第一阶段仍需完成作者 L4、作者报告、历史测试改动确认及新导出协议等收尾；不因本次文档更新而标记阶段完成。收尾证据见 [核对记录](docs/stage1_readiness.md)，下一阶段准备及待决事项见 [交接摘要](docs/stage2_handoff.md)。

## 复现存档结果

需要 Python 3.10 或更高版本及 `requirements.txt` 固定的 Inspect 0.3.278；本机已验证环境为 Python 3.14.6。首次安装依赖需要网络；复核存档本身不调用模型 API，不需要 API key。

在仓库根目录准备环境：

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

一条命令复核现有存档：

```sh
.venv/bin/python -B scripts/reproduce_stage1.py
```

它运行完整测试与现有数据验证，检查冻结任务、日志及运行凭证的哈希，核对 24 次实际输入和评分诊断，重新导出 CSV 与汇总并逐字节比较。结果写入独立的 `results/reproduced_stage1/`，原始存档保持原样；任一检查失败即以非零状态退出。现有数据验证器尚未覆盖 PROJECT_SPEC 第 4.4 节的全部要求，不能将它的 PASS 视为完整任务审计。

仅运行测试：

```sh
.venv/bin/python -B -m unittest discover -s tests -v
```

新模型运行、模型选择、采样参数和预算须事先明确。上面的复现命令只复核存档，不发起新运行。
