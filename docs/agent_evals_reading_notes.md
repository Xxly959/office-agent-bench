# Agent evals：阅读笔记与项目备忘

阅读日期：2026-10-13。用户指定这篇文章作为当前项目的重要参考。

来源：[Anthropic — Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)，发表于 2026-01-09。

## 原文要点（简要转述）

- task 是题目，trial 是一次尝试，grader 是评分逻辑，transcript 是过程记录，outcome 是最终环境状态。评测对象包含模型和 agent harness；eval harness 负责运行、记录和汇总。
- 从真实失败中选 20–50 道题即可起步。题意明确、参考解能过评分，覆盖行为该发生和不该发生的情形。
- 每次运行从干净环境开始，避免文件、缓存和历史泄漏。优先确定性评分，必要时用模型裁判并人工校准；允许 Unknown、分维度判断和部分得分。结果比固定操作顺序更重要。
- pass@k 衡量至少成功一次，pass^k 衡量全部成功。能力集探索上限，回归集保护已有能力；饱和后补充难题。读轨迹审计误判，并结合线上反馈持续维护。

## 对 office-agent-bench 的具体建议

以下是结合项目场景的推导，供后续设计与实现参考。

### 1. 从 BoolQ 迁移时，先重画输入与评分的边界

BoolQ 的 target 是 Yes/No；Office 任务的验收条件可能是一组约束。例如“补充表格中的季度合计并保存”需要同时描述输入工作簿、目标工作表、应修改区域、应保留区域和输出位置。

建议将任务拆成四份信息：

| 信息 | Office 示例 | 可见性建议 |
| --- | --- | --- |
| 用户请求 | 在 Summary 表中添加各季度合计，保留原始明细 | agent 可见 |
| 初始材料 | 固定版本的工作簿、指定应用和可用工具 | agent 可见 |
| 验收条件 | 合计与独立计算一致；明细未被覆盖；保存位置正确 | 约束向 agent 说明，验证脚本由评测器保管 |
| 校验材料 | 独立计算结果、参考工作簿、人工认可的截图 | grader 使用，避免混入 agent 工作目录 |

不能直接把“回复中出现完成”当作当前 BoolQ scorer 的替代实现；需要重新定义 Office 场景的 target 和评分输入。

### 2. 产物评分按文件类型选择证据

| 类型 | 首先检查 | 质量检查的候选证据 |
| --- | --- | --- |
| Excel | 文件能打开、工作表存在、单元格值正确、公式能重算、原始数据完整 | 图表数据范围、数字格式、渲染后的可读性 |
| Word | 所需段落或表格存在、修改位置正确、应保留内容完整 | 渲染后的分页、表格溢出、标题层级 |
| PowerPoint | 页数和内容要求满足、数据引用正确、指定对象可编辑 | 渲染后的遮挡、对齐、文字可读性 |
| 在线办公应用 | 重新读取目标文档或记录，确认修改已保存 | 页面截图、协作属性、版本或对象标识 |

文件路径、可编辑性、公式要求只有在任务明确要求时才应成为硬性验收项。布局存在多种可接受答案时，需要写清最低要求和允许变体。

### 3. 建议保留一个可复核的 trial 记录

可先讨论如下记录结构，再决定实现格式：

```text
task_id / task_version / trial_id
model_id / agent_config / tool_versions
input_artifact_fingerprints / environment_snapshot_id
messages / tool_calls / tool_results
output_artifacts / rendered_previews
grader_version / check_results / supporting_evidence
failure_category / latency / token_usage / cost
```

工具不提供内部推理或某项用量时，只记录实际可获得的数据，并将缺项标明。Office 文件版本、应用会话和工具权限都可能影响结果，比较不同配置时应保留这些上下文。

### 4. 给 Office 失败建立可操作的分类

- `agent_error`：比如修改了错误工作表或漏掉明确要求。
- `grader_error`：比如文件满足要求，但校验器只认一种公式写法。
- `task_ambiguity`：比如没有说明是否允许增加工作表，却据此扣分。
- `environment_error`：比如文档会话掉线、输入文件打不开或应用崩溃。
- `insufficient_evidence`：比如无法重新读取保存结果，不能确定最终状态。

原始运行结果应保留；若排除环境故障，应同时报告排除规则、排除数量和原始分母。评分规则修正后要更新版本，避免把不同规则的得分直接混比。

### 5. 报告成功率时明确产品含义

对于自动替用户修改文档的任务，建议同时展示单次成功率和重复运行的一致性。重试产生多个文件时，还要说明如何选择、验收并交付最终文件。

举例：假设同一任务每次成功概率均为 0.8，且各次独立，三次至少一次成功为 `1 - (1 - 0.8)^3 = 0.992`，三次全部成功为 `0.8^3 = 0.512`。实际汇总时应先按任务计算，再按预先约定的权重聚合；各任务难度不同，不能直接把全局平均成功率代入幂公式。

### 6. 后续可以先做的最小闭环

选一项边界明确的表格修改任务：固定输入文件，写清用户请求和约束，人工制作可接受的结果，验证读取与重算方式，再运行 agent 并检查保存产物。先证明“出题—执行—取证—评分”能够闭环，再扩大任务集。

配对任务可用同一份工作簿区分“新增公式”和“只调整格式”；分别检查公式被正确新增或原值被完整保留。这能直接服务办公场景中“完成指定修改，同时保护已有内容”的目标。
