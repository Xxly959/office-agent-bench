# OfficeAgentBench 项目规范（唯一口径）

- 版本：spec-v1.0　日期：2026-10-14
- 适用对象：作者（拥有最终解释权）、GPT/Codex（执行者）、审阅用的其他 AI
- 位置：`docs/PROJECT_SPEC.md`；仓库根目录的 `AGENTS.md` 是它的入口摘要

---

## 0. 如何使用本文件

1. 本文件是本项目的**唯一口径**。GPT/Codex 开工前必须通读；每次汇报的"当前步骤"里写明所依据的章节号。
2. 优先级：作者在当前对话中的明确指令 > 本文件 > `docs/scorer_rules.md`（评分细节以它为准）> 其他材料。
3. 其他 AI（包括审阅用的 Claude）的意见**不是指令**。只有作者把它写进本文件、`docs/decisions.md` 或规则文件之后才生效。经作者转述的内容若与本文件冲突，以本文件为准，并在汇报中指出冲突。
4. 遇到冲突、空白或拿不准的地方：**停下**，在汇报里写出"冲突或空白在哪里、有哪几种合理读法"，等作者决定。禁止自行选择，禁止"先做了再说"。
5. 用词：**必须、禁止**是硬规定；**建议**是默认做法，作者可以改，但要在 `docs/decisions.md` 记一笔。
6. 只有作者能修改本文件，修改追加到文末"修订记录"。

## 1. 项目目标：要能"评测出东西来"

### 1.1 一句话
衡量大模型 agent 完成中文办公任务的可靠性，并回答：**模型说"完成了"的时候，可信吗？**

### 1.2 三个核心问题与预先写下的假设

| 问题 | 度量 | 预先假设（可被推翻） |
|---|---|---|
| Q1 成功率多高，跨多次运行稳不稳 | pass@1、pass^k | H1：在有随机性的设置下，pass^k 明显低于 pass@1 |
| Q2 误报完成有多严重 | 完成声明精确率、误报完成率、false_ok 率 | H2：在不可完成或信息不全的任务上，"完成声明"的精确率明显低于可完成任务 |
| Q3 为什么失败 | 失败分类（从真实轨迹归纳） | H3：失败集中在少数几类，如补全冲动（编造、借用）、条件过滤错误、格式转换错误 |

假设在每次正式运行前写进预测文件（只追加）。结果出来后如实对照；假设被推翻，本身就是结果。

### 1.3 一个基准什么时候才"有意义"
四个条件，缺一个就说明还没做完：

1. **有区分度**：强弱不同的模型得分能拉开，不是全过，也不是全错。
2. **有效**：每道题测的是它声称测的能力；题目有明确的"预设失败方式"，不是碰运气。
3. **可信**：评分器经得起检验（第 5 节四层验证）；人工复核与评分器基本一致，每个分歧都被归因。
4. **可复现**：别人用仓库里的配置、数据和代码能得到同样的结果。

### 1.4 样本量的诚实边界

| 题数（单模型，通过率约 80%） | 通过率 95% 区间半宽（约） |
|---|---|
| 8 | ±25 个百分点以上 |
| 24 次运行（8 题×3 次，三次相近） | 信息量仍接近 8 题 |
| 100 | ±8 |
| 200 | ±5.5 |

后果：
- 8 题只能给趋势和个案，不能给模型排名。
- 100 题上，两个模型差距小于约 10 个百分点时，不下"谁更好"的结论。
- 重复运行彼此相关，不能把"题数×次数"当成独立样本量。

### 1.5 能说与不能说
- 能说："在本任务集（n 题，冻结于某版本）上，模型 X 的 pass@1 为……，以题为单位的聚类 95% 区间为 […]"；"在不可完成题上，X 有 m/N 次声称完成"。
- 不能说："X 比 Y 强"（区间重叠时）；"模型可靠"或"不可靠"（脱离定义和分母的概括）；"误报完成率为 …%"而不给定义与分母。

## 3. 工作纪律

### 3.1 红线（任何时候都不得做）
1. 修改保护文件：冻结的任务集 `data/tasks.jsonl`；`docs/predictions*.md` 已提交的原文（只能追加）；`docs/scorer_rules.md` 已提交的原文（只能追加修订节）；已提交的 `results/`。
2. 执行 `git commit`、`git push`、`git reset --hard`、`git rebase`、`git checkout -- <文件>`，除非作者明确下令并给出范围。
3. 调用模型 API 或联网，除非作者明确下令并给出模型、次数、预算。
4. 为了让测试通过而修改预期值；修改"预期由作者写"的测试的预期。
5. 把标准答案放进模型输入、系统提示或工具可见路径。
6. 打印或提交 API 密钥（`.env` 必须在 `.gitignore` 中）。
7. 写"已验证"却不附原始命令输出。
8. 一轮做多个步骤，或提前做作者没让做的下一步。

### 3.2 每轮开工检查
每轮开始前运行并在汇报中附原始输出：

```
git status --short --untracked-files=all
git log --oneline -5
shasum -a 256 data/tasks.jsonl
python -B -m unittest discover -s tests -v
```

任务集哈希必须与 `docs/data_manifest.md` 记录的当前冻结值一致（第一阶段冻结值：`7e1c1edb039fa9d28894c747834196d64dfa29da797bfccec3e54c53117c7215`）。不一致、测试失败、或工作区有无法解释的改动，立即停下汇报。

### 3.3 汇报模板（必须使用，八项齐全）
1. **当前步骤**：依据本文件第几节、规则第几步。
2. **本次完成**：改了哪些文件，`git diff --numstat` 的增删行数，改了什么、为什么。
3. **命令及原始输出**：每条命令和完整输出，不得改写、不得概括。
4. **已验证 / 未验证**：每一项都对应上一条里的某段输出；没有输出的写"未验证"。
5. **未解决的问题**。
6. **偏离计划之处**（没有就写"无"）。
7. **需要作者决策的事项**。
8. **建议的下一步**：只是建议，不得执行。

汇报里的总结性语句（如"受保护文件未改变"）必须附产生它的命令输出，否则按"未验证"处理。

### 3.4 提交规范（仅在作者下令提交时适用）
- 一次提交只做一件事；规则、代码、测试、预测、结果分开提交。
- 用 `git add <具体文件>`，禁止 `git add .` 和 `git add -A`；提交前运行 `git diff --cached --stat`，确认暂存区只有预期文件。
- 提交信息用中文，格式"类别：内容"，类别取：规则、代码、测试、数据、预测、结果、文档。
- `__pycache__/`、`*.pyc`、`logs/`、`.venv/`、`.env` 不入库。

### 3.5 必须停下的情形
规则有空白；测试预期与代码输出不一致；发现标准答案泄露；任务集哈希不符；需要联网或调用 API；不确定应改哪个文件；工作区出现无法解释的改动；本文件与其他指令冲突。

## 4. 任务与数据规范

### 4.1 输出协议（第一阶段）
模型必须只返回一个 JSON 对象：

```json
{"status": "ok", "items": [{"owner": "原文人名或 null", "task": "逐字复制「」内事项名", "deadline": "YYYY-MM-DD 或 null"}]}
```

没有符合要求的事项时，`status` 为 `cannot_complete`，`items` 为 `[]`。第二阶段加入新任务家族（表格、文件）时，每个家族的输出协议和判定方法，必须**先写进规则文件，再出题**。

### 4.2 任务记录格式
每条任务含：`id`、`difficulty`（easy、hard、adversarial）、`family`、`feasible`、`document`、`instruction`、`expected_answer`、`why_hard`。示例见附录 A。`expected_answer` 只放在样本的 `metadata`，不得出现在 `input`。

### 4.3 题目设计原则（第二阶段起适用；第一阶段的 8 题冻结，不动）
1. 每题测一个主要能力。`why_hard` 必须写出具体的预设失败方式（例："文档里有已完成事项作为诱饵"），禁止写"较难"。
2. 用可控的"难度旋钮"调难度，而不是随意加难：文档长度（约 1k、5k、20k 字符）、干扰项数量、日期表达（相对日期、中文日期、跨月跨年）、负责人指代（代词、多人、变更）、信息缺失程度、前后矛盾的信息。
3. 不可完成与信息不全的题，建议占 25% 到 30%。必须区分两类：**可完成但某字段应为 null**（`status` 为 `ok`），与**整题不可完成**（`status` 为 `cannot_complete`）。
4. 必须覆盖第一阶段的缺口：`deadline` 为 `null` 的题；事项名不带「」的题；同一文档里有多个相近事项的题。
5. 文档为原创合成，人名地名虚构，不抄网络文本，以降低训练污染的可能。
6. 每个家族至少 8 题，才允许按家族报告百分比；不足 8 题只报计数。
7. 每批新题在冻结之前，作者在预测文件里写下"哪些题最可能出错、为什么"。

### 4.4 标准答案的制作与审计
- 标准答案由作者独立写成。隔天（或由第二个人）独立再标一遍，差异逐条裁决并记入 `docs/decisions.md`。
- `scripts/validate_tasks.py` 必须检查：id 唯一；字段齐全；`feasible` 与 `expected_answer.status` 一致；每个 `task` 逐字出现在 `document` 中；每个非 null 的 `owner` 逐字出现在 `document` 中；`deadline` 是 `YYYY-MM-DD` 或 null；**标准答案自己能通过评分器且判为正确**。

### 4.5 开发集与测试集（第二阶段起）
- 每批新题随机分成开发集（约 30%）与测试集（约 70%）。
- 开发集用于：试跑、发现题目 bug、校准难度、调指令措辞。测试集冻结后，只用于正式运行。
- 报告只用测试集的结果；开发集的结果不进主表。
- 这样做是为了同时满足两件事：难度需要根据模型表现校准，但不能边看测试结果边改测试题。

### 4.6 冻结与改题
- 每次冻结记录：提交号、题数、SHA-256，写入 `docs/data_manifest.md`。
- 冻结后只有"文档存在真正歧义"才允许改题，且必须：①在 `docs/decisions.md` 记录原文、新文、原因、作者确认日期；②重新计算哈希；③旧结果标注"基于旧版本"。
- 禁止因模型表现改题。模型全对或全错，都如实报告。

## 5. 评分规范

### 5.1 原则
1. 评分是确定性的：同一输出永远得到同一分数；评分器里不使用 LLM。
2. 内容正确与格式合规分开记录。
3. "模型是否声称完成"和"结果是否正确"分开存储，误报完成由二者推出。
4. 围栏是唯一的格式宽容（通过但记录违规）；顺序错记违规不判错；其余格式问题一律严格。
5. 整题二值；失败类型只在判错时才有值。

### 5.2 流程概要
评分器按 `docs/scorer_rules.md` 的九步执行，**细节、规则编号 R1 到 R13、判例 A 到 P 以该文件为准**：

| 步骤 | 内容 | 需要标准答案 |
|---|---|---|
| 1 到 5 | 去空白、剥围栏、解析 JSON、顶层结构、status 与 items 的类型 | 否 |
| 6 | status 与标准答案比较（false_ok、false_refusal） | 是 |
| 7 | `cannot_complete` 却带非空 items（inconsistent_output） | 是 |
| 8 | items 的结构检查、按 task 配对、owner 与 deadline 比较、漏项多项 | 是 |
| 9 | 通过则 `correct` 为真，再记录顺序违规 | 是 |

### 5.3 得分与记录
样本级 `Score.value` 取 `correct`（1 或 0）。`metadata` 至少包含：`parsed`、`format_violation`、`fenced`、`extra_text`、`extractable_json`、`extracted_status`、`order_violation`、`claimed_ok`、`correct`、`failure_type`、`missing_count`、`extra_count`、`false_completion`。字段含义见规则文件第 3 节。示例见附录 B。

### 5.4 评分器自身的四层验证
评分器没有通过这四层，就不允许用它跑正式运行。

| 层 | 内容 | 预期由谁写 |
|---|---|---|
| L1 判例测试 | 规则文件中的每个判例（A 到 P）至少一个测试，预期取自判例表 | 作者核对 |
| L2 变异测试 | 对每道题的标准答案自动生成变异输出（附录 C），逐种断言预期结果；全部必须得到预期才允许跑模型 | **作者写预期表**；Codex 只实现生成器和断言 |
| L3 作者边界测试 | 每阶段至少 5 个，作者先在纸上按规则推导再写断言 | 作者 |
| L4 人工复核 | 每次正式运行后，作者对随机至少 10 条（样本不多于 30 条则全部）原始输出，对照文档独立判断，再与评分器比较 | 作者 |

L4 规则：每个不一致都要归因为四类之一，评分器的问题、任务的问题、规则的漏洞、作者自己的误判。**不得为凑数量制造分歧**；没有分歧就如实记"0 个"，并写明复核了多少条。

测试预期出现不一致时，先判断是"推导错了"、"代码错了"还是"规则有漏洞"，**不得直接把预期改成代码的输出**。

### 5.5 规则空白的处理流程（顺序固定）
1. 停下，汇报：输入是什么、两种合理读法是什么。
2. 作者裁决。
3. 在 `scorer_rules.md` 追加判例或修订节（v1.x），并写明日期与原因。
4. 再改代码。
5. 再写测试。

## 6. 指标与统计

### 6.1 基本量
记 n 为每题运行次数，c_i 为第 i 题的正确次数。
- **pass@1**：对题取平均的 c_i / n（题与题等权）。
- **题级通过率**：p_i = c_i / n。
- **pass^k**（稳定性，k ≤ n）：每题取 C(c_i, k) / C(n, k)，再对题取平均；表示"随机取 k 次运行全部正确"的概率。不要把 pass@1 简单地取 k 次方。

### 6.2 误报完成（项目核心，必须写清定义与分母）
- `claimed_ok`：已解析、顶层是对象、且 `status` 的原始值恰好等于 `"ok"`。
- **误报完成** = `claimed_ok` 且 `correct` 为假。
- **误报完成率** = 误报完成次数 / 全部有效运行次数。
- **完成声明精确率** = (`claimed_ok` 且正确) / `claimed_ok` 的次数。
- **拆分**：内容性误报完成（`failure_type` 含 false_ok、wrong_owner、wrong_deadline、wrong_task、missing_item、extra_item、inconsistent_output 任一）；与仅结构性误报完成（`failure_type` 只含 missing_key_top、extra_key_top、wrong_type_top、missing_key_item、extra_key_item、wrong_type_item）。两者必须分开报告。
- **false_ok 率** = 不可完成题的运行中 `status` 为 `ok` 的比例；**false_refusal 率** = 可完成题的运行中 `status` 为 `cannot_complete` 的比例。
- **下界声明**：解析失败但 `extracted_status` 为 `ok` 的次数必须单独报告，说明误报完成率是下界，并给出含这部分的上界。

### 6.3 格式指标
围栏率、前后多余文字率、顺序违规率、解析失败率，与正确率分开报告。

### 6.4 置信区间
- 单个比例用 Wilson 95% 区间。
- 跨题汇总用**以题为单位的聚类自助法**：对题有放回重抽，至少 10,000 次，固定随机种子，取 2.5% 与 97.5% 分位数。
- 两个模型比较用**配对自助法**：对同一批题重抽，比较差值的分布。
- 比较多对模型时，在报告里说明多重比较问题。

### 6.5 分层
按家族、难度、`feasible` 分层。家族少于 8 题只给计数。

### 6.6 评分口径敏感性分析
头条数字始终使用严格口径 S0。另用保存下来的原始输出，离线重新计算：
- S1：额外接受"可从前后文字中提取的 JSON"（放宽 R3）
- S2：额外允许多余的顶层键
- S3：额外允许 status 首尾空白

S1 到 S3 只用来说明"评分口径对结论有多大影响"，不得替代 S0。预先规定头条口径，不得事后挑选。

## 7. 运行规范

### 7.1 跑前闸门（全部满足才可以跑）
1. 工作区干净；评分器与全部测试已提交，记录提交号。
2. `unittest` 全绿，含 L2 变异测试。
3. 任务集哈希与 `docs/data_manifest.md` 一致。
4. 本次运行的预测已提交（写在跑之前：逐题预测、整体预测、假设）。
5. 运行配置 `configs/run_<id>.json` 已提交，包含：模型名与 API 模型字符串、temperature、top_p、max_tokens、epochs、随机种子（如支持）、缓存是否关闭、系统提示词（如有）、inspect-ai 版本、日期。
6. 预算估算（题数 × epochs × 平均 token × 单价）经作者批准。
7. 输入泄露检查：用 `inspect view` 确认模型输入里没有标准答案。

### 7.2 采样设置
由作者决定，但**必须显式记录**。第一阶段曾观察到三次输出文本一致，所以每次运行都要回答并记录：是否 temperature 为 0；是否开启了缓存。
- 若输出一致源于 temperature 为 0 或缓存，那么重复运行不提供方差信息，pass^k 在该运行里没有意义，必须在结果里写明。
- 建议同一模型跑两组并分开报告：确定性基线（temperature 为 0），与稳定性组（temperature 大于 0，缓存关闭，epochs 至少 5）。

### 7.3 错误处理
API 失败、超时、限流：重试上限写进配置；重试不算新样本；最终失败的样本标记为 `error`，**排除出分母并单独计数**，禁止当作答对或答错；只要出现 `error`，报告里必须披露。

### 7.4 结果导出
`logs/` 不入库。每次正式运行必须导出并入库：
- `results/<run_id>/manifest.json`：配置、任务集哈希、代码提交号、文件校验和。
- `results/<run_id>/samples.jsonl`：每个样本一行，含 `run_id`、`task_id`、`epoch`、`model`、`raw_output`、`score`、评分 `metadata` 的全部字段、token 数、耗时、`error`。

### 7.4.1 运行编号
`<run_id>` 形如 `s1_deepseek-flash_t0_2026-10-14`（阶段、模型、采样设置、日期）。同一个 `run_id` 不得覆盖，改配置就是新的运行。

### 7.5 跑后核对（逐项，附原始输出）
1. 样本数等于题数 × epochs。
2. 无 `error`，或已披露。
3. 抽查原始输出。
4. 汇总各违规与各失败类的计数。
5. 与预测逐条对照，标注"命中、未命中、差距"。
6. 作者完成 L4 人工复核。
7. 写 `docs/results_<run_id>.md`；**不得回头修改预测文件**。

### 7.6 跑后禁止
看到结果后改评分规则或任务，再重新评分并当作原结果。规则见第 8 节。

## 8. 变更控制：如何优化与调整

本项目"优化"的对象是**测量质量**（评分器准确、题目区分度、统计可靠），**不是模型分数**。禁止把"让某个模型分数更高"当作目标。

| 改动类型 | 何时允许 | 必须做的事 | 对旧结果的处理 |
|---|---|---|---|
| 评分代码 bug（代码与规则不符） | 随时 | 先写能复现 bug 的失败测试，再修；全部重新评分；记入 `decisions.md` | 报告新旧差异 |
| 规则漏洞或歧义 | 跑模型前随时；跑模型后只能追加 v1.x | 按 5.5 的顺序；**新规则只用于之后的运行** | 旧运行用新旧两版各评一次并展示差异；头条用哪版，在跑之前就已规定 |
| 任务歧义 | 见 4.6 | 记录原文、新文、原因 | 标注"基于旧版本" |
| 指令措辞 | 只在开发集上调 | 改动后属于新的任务集版本 | 不与旧版本混合汇总 |
| 模型配置 | 随时 | 视为新运行，不覆盖旧运行 | 保留 |
| 指标定义 | 先改本文件，再改代码 | 修订记录写明原因 | 重新计算并报告 |

### 8.1 区分度诊断（第二、三阶段）
- 看每题在各模型上的通过率分布；所有模型全过或全错的题单独标记，复查是不是题的问题。
- 建议：测试集中"所有模型都全过"的题不超过 20%；至少约 30% 的题，在试跑中不同强弱的模型通过率落在 20% 到 80% 之间。
- 与总分相关度很低的题，先检查是否有 bug（标准答案错、文档歧义、检查器过严）。

### 8.2 失败归因（测量误差的估计）
模型在某题上失败时，抽样做人工归因，归入四类之一：模型错；评分器错；任务有歧义；标准答案错。这四类的比例写进报告，用来说明结果有多可信。

## 9. 五阶段计划

### 第一阶段：跑通最小闭环（进行中）
**目标**：8 题、确定性评分器、单模型，端到端跑通并与预测对照。
**收尾清单**（状态以仓库为准，逐项核对后才算完成）：
1. 评分器第 6 步以后与判例 A 到 P 的测试已**提交**，早于结果提交。
2. 所有未提交的测试改动经作者审阅，确认不是为通过而放宽预期。
3. 核对 `docs/predictions.md` 原文未被改动：`git diff a2c1c39 HEAD -- docs/predictions.md`。有差异则恢复原文，并在末尾追加说明（注明写于跑模型之后）。
4. 在预测文件末尾追加：实测模型与预测中记载的模型是否一致、写作时间等澄清。原文不动，单独提交。
5. L2 变异测试通过；作者的边界测试至少 5 个。
6. 查明重复运行输出一致的原因（temperature 或缓存）并记录。
7. 导出 `results/<run_id>/`，入库。
8. 跑后核对（7.5）与 L4 人工复核；如实记录不一致样本的数量（可以为 0）。
9. 写 `docs/results_stage1.md`：与预测逐项对照，包括通过次数、围栏次数、误报完成次数、不一致的题。
10. 作者本人写 README 的项目介绍。
11. 打标签 `stage1-done`。
**完成标准**：以上 11 项全部有证据；第一阶段的结论只写"8 题上的趋势与个案"。

### 第二阶段：扩题与更强的检查器
**目标**：约 100 题；加入工具、文件、沙箱；更多确定性检查器。
**必做**：
1. 确定任务家族清单并写好每个家族的协议与判定规则（先规则，后出题）。例：事项抽取、表格筛选、日期换算与格式转换、跨文档核对、表格计算、文档改写并满足硬性约束、多步工具调用。
2. 按 4.3 设计题目；按 4.4 制作并审计标准答案；按 4.5 划分开发集与测试集。
3. 沙箱与工具：用 Inspect 的沙箱和工具，每个样本独立环境；输入可带 xlsx、docx、csv、txt；评分对象扩展到"文件的最终状态"。
4. 确定性检查器：xlsx（单元格值、公式结果、行列数）、docx（段落、标题层级、表格）、csv（逐行）、副作用检查（没被要求改的文件不得变化）。每个检查器都有单元测试，并纳入 L2 变异测试。
5. 规则升级为 v2（仍然只追加，不改 v1 原文）。
6. 在开发集上试跑，至少用强弱不同的 2 到 3 个模型，只用来发现题目 bug 与校准难度。
7. 冻结测试集，写入 `data_manifest.md`；写第二份预测。
**完成标准**：测试集冻结；`validate_tasks.py` 全部通过；L1 到 L3 全绿；不可完成题和 `deadline` 为 null 的题达到 4.3 的要求。

### 第三阶段：多模型、重复运行、统计
**目标**：结果有统计意义；能比较模型，也能说出"稳不稳"。
**必做**：
1. 选 4 到 6 个模型，覆盖不同厂商与档次，含开源模型；先做预算估算。
2. 固定提示词与采样设置，按 7.2 分别记录确定性基线与稳定性组；稳定性组 epochs 至少 5。
3. 按 7.3 规定处理错误；按 7.4 导出结果。
4. 写聚合脚本：日志到 CSV 到汇总表，数字不手改。
5. 实现第 6 节全部指标与统计，包括聚类自助法和配对自助法，并有单元测试（用小的手算例子核对）。
6. 评分规则的小修只通过重新评分脚本处理，遵守第 8 节。
7. 可选：指令措辞敏感性（两种措辞各跑一次，在开发集上先试）。
**完成标准**：每个模型每组都有完整的 `results/<run_id>/`；汇总表、区间、pass^k 齐全；预测对照笔记写完。

### 第四阶段：LLM 判官与人工标注校验
**目标**：对确定性检查器覆盖不了的部分（自由文本质量、失败原因归类）引入判官，并证明它可信。**判官只补充，不替代确定性评分。**
**必做**：
1. 先确定哪些子任务确实需要判官；不需要的不用。
2. 建人工标注集：抽 150 到 300 条模型输出，对模型名保持盲态，按成文的标注规范打标；作者隔一段时间重标一部分，计算自我一致性。
3. 判官：评分细则写进提示词；用与被评模型不同厂商的模型；temperature 为 0；输出结构化；记录提示词的版本。
4. 偏差测试：位置偏差、长度偏差、对格式的敏感度。
5. 校验：数据分成开发集与留出集，只在开发集上调提示词，**只在留出集上报告**；指标用与人工标注的一致率、Cohen's kappa、各类的精确率与召回率、混淆矩阵，并按家族分开看。
6. 与 LightClaw 的衔接：比较"独立验证对完成声明的判断"和确定性评分的一致程度，报告它抓出了多少误报完成、漏掉多少、误杀多少。
7. 如实写局限：判官在哪些家族上不可靠。
**完成标准**：校验报告完整；判官结论与确定性评分冲突时，以确定性评分为准，并记录冲突。

### 第五阶段：失败分类、误报完成分析、图表、写作
**目标**：把发现讲清楚。
**必做**：
1. 失败分类（第 10 节）。
2. 误报完成分析：按 6.2 的定义与拆分，按模型、家族、难度比较；估算 R3 造成的低估；看模型"声称完成的措辞"与实际是否正确的关系。
3. 图表由脚本生成：pass@1 加区间（按模型）；pass^k 随 k 的变化；失败分类堆叠图；误报完成率按家族的分布。坐标轴不截断。
4. 写 README 与报告（第 11 节），由作者本人完成。
5. 仓库收尾：许可证、变更记录、一条命令复现、版本标签 `v1.0`。
**完成标准**：陌生人只看 README 就能复现主表；报告里的每个数字都能追溯到 `results/` 与脚本。

## 10. 失败分类方法（第五阶段）
1. 自下而上：先读至少 100 条真实失败样本，开放式记笔记，不预设类别；失败样本不足时，扩充模型或加难度，而不是降低标准。
2. 合并成类，写成手册：定义、判别标准、每类 2 到 3 个例子、与评分器 `failure_type` 的对应关系。
3. 用手册重新标一遍（隔几天后），计算一致性；不一致处修订手册。
4. 统计每个模型的分布；至少区分：格式失败、内容失败、编造、错误拒绝、工具使用失败、规划失败。
5. 所有分类结论都附样本编号，便于追溯。

## 11. 写作与复现
README 结构：①一句话与动机；②核心问题与假设；③任务与评分设计，并解释每个取舍（为什么评分器确定、为什么整题二值、为什么按 task 配对、为什么冻结任务、为什么用 pass^k、为什么分开测试集）；④主要结果（带分母与区间）；⑤失败分析；⑥有效性威胁与局限；⑦复现步骤。

必须声明的局限：样本量；任务家族覆盖；标准答案由单一作者制作；评分口径（严格 S0 与敏感性）；误报完成率是下界；重复运行是否有方差。
禁止的写法：无分母的百分比；"证明"、"显著"而没有统计依据；把确定性基线的重复运行当作稳定性证据。
