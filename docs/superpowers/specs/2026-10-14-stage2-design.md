# 第二阶段设计草案：100 条文件与工具任务

日期：2026-10-14（Asia/Shanghai）。Codex 提案，待项目作者审阅规则与取舍；本文件不是已经冻结的 v2 规则，也不是事前预测。第一阶段数据和规则原文继续保留。

## 目标、范围与成功标准

把当前 8 条文本题的闭环扩展为 100 条办公任务，加入 csv、txt、xlsx、docx 文件及逐样本 Docker 沙箱。内容正确、结构合规和完成声明分别记录；确定性检查仍决定整题的 1/0 分数。判官、多模型正式比较及最终报告保留到后续阶段。

完成条件：100 条记录及全部输入资产通过 schema、唯一 id、文件哈希与标准答案自检；每个检查器有正确结果和失败边界测试；抽取 15 条做独立标注，公开一致率及争议处理；小模型预跑只用于发现任务 bug，修订均留记录；随后冻结 v2 规则、数据、输入资产、提交号和 SHA-256，并在正式跑模型前提交作者的第二份预测。

Codex 实现代码和校验、保存原始输出；作者决定任务、答案、规则判例和取舍并审阅全部代码。需要作者独立写的预测、复核结论和报告不得标成 Codex 已代替完成。

## 方案与建议

可选方案有三个：一次写齐全部家族；先实现所有检查器再集中写题；先以每家族一个完成样例和一个不可完成样例贯通，再分家族扩充。

建议第三种。先用 14 条开发题验证文件传递、状态语义、检查器与无泄露边界，随后扩充到 100 条。它把错误暴露在未冻结的开发阶段，不用在已经产生正式结果后改题；每个家族独立完成后就可以审阅。开发题可进入最终 100 条，但经过小模型预跑且修订记录公开，必须在正式结果前冻结。

## 状态语义与模型输出

v1 的 cannot_complete 表示“没有符合要求的事项”，只有 office_007 一题。这不等同于文件代理无法完成任务。v2 建议：有足够信息完成操作，即使合法结果为空，也返回 ok；只有缺少指令要求的必要资源、关键信息且不允许 null、或相互矛盾的硬约束无法同时满足，才返回 cannot_complete。

不可完成题必须能由作者和确定性条件核实原因。例如缺少被要求读取的文件、日期转换缺少必需参考年且明确禁止猜测、总额与固定各行数值要求互相矛盾。仅困难、空筛选结果、可表达的 null，不计入这 25 条。

v2 统一最终 JSON 顶层仅含 status、items、outputs。status 仍是 ok/cannot_complete；items 是列表，按家族的 schema 检查；outputs 是仓库相对输出路径的列表，必须与任务约定相符，拒绝绝对路径和越界路径。文件任务的 items=[]，JSON 结果任务的 outputs=[]。cannot_complete 时二者均为空，原始输入文件应保持不变。

完成声明仍来自已解析对象的 status==ok。检查器读取预先指定的输出文件，不能只相信模型声明的路径、内容摘要或完成措辞。每个文件任务要求最终 JSON，但即使 JSON 失败也读取预期文件做内容诊断，以区分内容错和仅结构错；协议不合规时整题仍不通过。宽松提取只作诊断，沿用 v1 的 R3 分离原则。

新增 content_correct、structure_correct 与 failure_type；保留 correct、claimed_ok、false_completion、extractable_json、extracted_status。correct=content_correct 且 structure_correct；规则允许的围栏和顺序违规单列而不影响内容通过。false_completion 的拆分为 claimed_ok 且内容错误，与 claimed_ok 且内容正确但结构错误，互斥。任务状态错误归内容错误。

## 检查器设计

每个检查器只读取最终状态和宿主标准答案，返回布尔结果、失败类型及诊断。路径处理与副作用验证共用组件；JSON 和各文件格式分别处理，不用模型判官。

- JSON：schema、枚举、null 类型、集合与顺序分开。未加引号的事项仍要求复制原文；只去首尾空白。如确需别名，作者在冻结前枚举可接受值，禁止见到模型输出后补白名单。不引入不受约束的模糊匹配阈值。
- csv：UTF-8，按标准 CSV 引号规则读字段；记录是否含表头及要求的行顺序，比较行列数和每个字段。文本不擅自把 001 改成数字 1。数字字段依任务明确的精度与舍入规则比较。
- xlsx：openpyxl 检查工作表、行列范围、值和公式。若指令要求公式，值正确而无公式仍不通过。openpyxl 本身不计算公式，因此不把 data_only 的缓存值当成独立证据。开发阶段仅支持预先列出的公式语法：SUM、AVERAGE、单元格/矩形引用和四则运算；宿主用独立受限解析器计算，禁止执行任意字符串。超出该语法的题暂不纳入 v2。缺失缓存不单独判错，结果由宿主计算；明确规定空单元格、除零及金额舍入行为。
- docx：python-docx 检查段落文本、标题级别和表格单元格；以显式 style 和 outline level 规则识别标题。硬约束可以覆盖必含事实、禁词、标题层级、段落数、保留表格；自由写作质量暂不决定确定性分数。字数按任务规定的字符计数方式计算，不把不同 tokenizer 混用。
- 副作用：未授权文件的新增、删除和内容变化都失败。完整未授权文件比较字节哈希；允许编辑的 xlsx/docx 则比较指定范围外的语义内容，避免把 ZIP 时间戳误算成无关正文修改。任务显式列 allowed_changes 和允许新建的输出路径；临时文件只允许在单独 scratch 目录，不计作交付文件。

官方依据：[Inspect Sandboxing](https://inspect.aisi.org.uk/sandboxing.html)、[Inspect Tools](https://inspect.aisi.org.uk/tools.html)、[openpyxl 公式说明](https://openpyxl.readthedocs.io/en/stable/simple_formulae.html)。实现时再核对仓库固定版本的本地 API，不能仅照抄最新文档。

## 数据、资产与沙箱边界

新建 tasks_v2.jsonl，保持 v1 tasks.jsonl 原样。v2 每条包含 id、difficulty、family、feasible、why_hard、instruction、input_files、checker、expected_answer、allowed_changes、coverage_tags。input_files 记录模型路径、宿主资产路径和 SHA-256；expected_answer 和 checker 配置只供宿主评分。

所有资产路径规范为 data/assets/v2/<id>/；模型只收到该样本选出的输入文件，挂载到 /workspace/input。输出在 /workspace/output，临时文件在 /workspace/scratch。任务文字明确资源列表、参考日期和输出路径。

每个样本、每个 epoch 使用独立 Inspect Docker 沙箱。工具只有 bash、python 和文件读写，所有执行通过 Inspect sandbox 接口；不得在宿主执行模型生成命令。固定镜像 digest 和依赖版本，关闭对外网络。标准答案、完整任务 JSONL、宿主代码仓库、检查器和评测日志不复制到镜像或容器，检查镜像层和启动脚本也没有答案。

评测前后列出模型可见路径，核对白名单；用 canary 标识测试宿主答案不可读取，并审阅 inspect view 中的实际消息和工具返回。泄露审计保存可见文件清单与检查结果，不能只搜 expected_answer 字段名。

## 独立标注、预跑与冻结

作者先按输入独立写标准答案，再抽样 15 条按家族、难度和可完成性分层复标。可由第二个人标注，或作者间隔数日后复标；记录身份、时间、是否盲于第一份答案。不能把 Codex 复制初始答案算作独立标注。分歧处理先定位任务歧义或答案错误，记录原因并重新验证。

小模型预跑不用于挑题、调难度或提高模型成绩。预跑发现答案错、文档歧义、检查器与成文规则不符才修订；每次保留原题、修订后题及原因。完成后冻结，正式模型结果不再触发任务修改。

冻结 manifest 记录数据/规则/所有资产的 SHA-256、提交号、镜像 digest、依赖锁文件和验证输出。commit 信息与 manifest 避免自引用：先提交数据规则和代码，再用下一次提交记录该提交号。正式运行要求工作区干净；运行配置显式记录 model、thinking、temperature、max_tokens、超时和重试政策。

预跑模型及 token 上限由实现完成后的预算估算决定，未经选择不调用收费 API。没有真实预跑、独立标注或 Docker 验证时，对应项保持“未完成”，不能只凭文件存在标成达标。

## 实现单元与验收顺序

1. v2 schema、资产清单和验证器：id 唯一、类型/枚举、配额、路径/哈希、状态与 feasible 一致性；标准答案必须通过对应检查器。
2. JSON、CSV、XLSX、DOCX 和副作用检查器：各自单元测试，失败诊断与规则判例逐条对应。
3. Docker 与工具闭环：先 14 条开发题；用确定性工具轨迹验证隔离、输出读取、完整日志和评分，之后再接模型。
4. 扩充 100 条、独立标注 15 条、泄露审计、小模型预跑及修订记录。
5. 冻结 v2，提交作者预测；明确所有固定参数后才开始下一阶段正式运行。

不在本草案阶段创建 100 条任务或升级正式规则。作者审阅的关键取舍是家族配额、空结果与不可完成的区别、复制/别名规则、公式支持范围及副作用定义；确认后再写可执行实施计划。
